# Observer-discovery comparison: development protocol v1

October 13, 2026. Freeze after the descriptive audit and before any comparative
execution. This protocol has not run. Its purpose is to test a candidate method,
not to establish novelty or promise repair superiority.

## Research question

Does source/trace-guided observation discovery improve independently verified
repair under a matched total budget, beyond native investigation and simple
execution/evidence normalization?

The audit's fifteen inspected instances are development-only and excluded from
later confirmation. Bug reports, enhancements, and refactors must have explicit
task-type labels. Primary fault-repair analysis uses reproducible reported bugs;
other task types are separately reported. Do not select based on Skylla success.

## Readiness and exclusion gates

Before comparative runs, establish a pinned environment with a reproduced target
failure and evaluator-only target/regression checks. Validate reset, actual source
origin, invocation limits, and complete tool logging. Missing images/dependencies,
irreproducible targets, and resource timeouts receive explicit dispositions.
Report every screened task and exclusion rather than quietly replacing failures.

The first pilot may use compatible audited bug tasks for apparatus development,
but their outcomes cannot support unseen generalization. Freeze the exact pilot
manifest, model/harness configuration, generator prompts, cost caps, seeds, and
observation adapters before execution. This document alone does not substitute
for those run-specific settings.

Current unresolved requirements: executable target environments, configured
model/harness access, a total inference budget, and independent repair checks.
Do not launch paid runs without those prerequisites. Offline auditing does not
satisfy them or evaluate a model-guided discovery method.

## Common capabilities and information boundary

All arms get the same issue, pinned source, native read/edit/test/debug tools,
reset behavior, execution and generation quotas, and observation presentation.
Native agents retain the ability to write probes and inspect internal state.
Never hand the proposed policy a correct observer field or evaluator mechanism
label. Evaluator tests, gold/reference fixes, and future repair outcomes are
inaccessible to generation/selection.

An observer proposal names the hypothesis or discrepancy it targets, its source
location and extraction, expected observable relation, preconditions, and estimated
full cost. Generate candidates from current code, issue, and execution traces.
Record proposals before executing them, including rejected, invalid, redundant,
and uninformative proposals. Failed setup supplies no causal rejection.

Preserve shell status and typed evidence separately. A caught exception at zero
exit, a collection failure that is the reported bug, or a printed surrogate result
must not be collapsed into a generic passing/setup label. Ambiguous role assignments
remain unknown. No universal confidence or coverage certificate is inferred.

## Comparison arms

| Arm | Purpose |
| --- | --- |
| Native harness | Actual incumbent investigation with equivalent tools and budgets |
| Native + generic review reminder | Attention/presentation control without privileged evidence |
| Native + cheap normalization | Correct source, project runner, encoding, and structured output handling |
| Native + blind observation generation | Same generator/quota as proposed arm; no adaptive routing |
| Native + source/trace-guided discovery | Proposed choice of new observation surface and candidate execution |

Begin with the native, normalization, and proposed arms to estimate feasibility
and costs. Add the attention and blind-generation controls before attributing
an effect to discovery/routing. Where feasible, include established coverage or
mutation-guided generation as strong additional baselines; do not describe a
simple sweep as a reproduction of those systems.

Use one model/harness first, then a separately configured replication before a
model/harness-independence performance claim. Cross-task menu order and run order
are seeded and shared across arms. Avoid fixed menus containing the evaluator's
useful observer: observer availability itself is part of the proposed method.

## Outcomes and costs

Primary outcome: target and regression verification of the final production
patch within the total cap. Evaluate without diagnostic instrumentation/mocks.
Do not use a model's self-declared completion or number of interesting logs.

Secondary outcomes: time/money/inference tokens, setup and generator failures,
invalid/redundant probes, useful candidate availability, unsupported conclusions,
and the burden of reproducing the result. Include source inspection, generation,
instrumentation, execution, resets, and verification costs; report evaluator-only
work separately. Preserve unsolved cases and censored timeouts.

Review observation usefulness independently and, where possible, replay paired
continuations from the same state. Such utility depends on the solver and budget;
it is not a universal causal label. Require a second reviewer or keep labels
exploratory. The current audit's labels are not sufficient to train a selector.

## Go/no-go and confirmation

If normalization or the reminder matches discovery, retain the simpler component.
If blind generation matches adaptive routing, drop the routing advantage claim.
If gains disappear after removing instrumentation, count those repairs as failures.
If only deliberately impaired menus improve, restrict the claim to that setup.

Use development variance, repository clustering, and full costs to set a minimum
useful effect and confirmatory sample size before confirmation outcomes are read.
Preregister the primary contrast, fixed configurations, multiple-comparison plan,
and failure accounting. The audited/development cases must not reappear in the
confirmation split. Small pilots may be inconclusive; do not turn lack of
significance into proof that methods are equal.
